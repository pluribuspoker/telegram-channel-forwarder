# Investigate

$ARGUMENTS

## Rules

1. **Detect your environment first.** Check if you're running locally (Windows) or on VPS (Linux, hostname `pickbot`). Use `uname -s` or check if `/home/forwarder/app` exists. This determines whether you SSH or run commands directly.
2. **Live data is on the VPS.** If local, SSH to VPS. If on VPS, run commands directly as forwarder.
3. **Telegram messages are accessible.** Use `scripts/vps_msg.py` on VPS. If local, run via SSH. If on VPS, run directly.
4. **Don't give up after one failed attempt.** Try variations before concluding data doesn't exist.
5. **Use a git worktree for code changes** (see CLAUDE.md worktree pattern). Do ALL commits in the worktree before merging.

## Workflow

1. **Detect environment**: Check if running on VPS or locally
2. **Gather context**: Fetch the Telegram message if linked, check parse_cache and/or DB
3. **Read the relevant code** before theorizing
4. **Verify VPS matches local** (if local): `ssh root@209.38.51.86 'cd /home/forwarder/app && git log --oneline -1'`
5. **Check VPS logs** (`journalctl -u telegram-tracker`, `journalctl -u grade-daemon`, etc.)
6. **Identify root cause**: Trace the full pipeline before fixing
7. **Fix and verify** with the real data that triggered the bug (replay actual inputs through the fixed code). **Output-changing fixes (a broadcast, edited message, rendered result): before declaring done, diff the new output against an existing known-correct analog (e.g. how the same thing renders in the non-buggy case) and match that format exactly — don't ship a reduced variant, and treat your own "cosmetic / moot / minimal / enhance-later" hedging as a signal to fix it now or ask, not to ship it.**
8. **Deploy code fix first** (push + deploy) before touching live data
9. **Fix live data** if needed (wrong emoji, DB entry, etc.). Use Bot API with `parse_mode: "HTML"` — check `msg.media`: use `editMessageCaption` for photo/video, `editMessageText` for plain text
10. **Run tracker manually** scoped to the affected channel for instant verification

## Lessons

1. Never inline Python in SSH commands beyond simple one-liners. Write a temp script, `scp` it, run it.
2. For grading bugs, trace the ENTIRE pipeline (`claude_parse` → post-parse → `validate_sport` → `build_context` → fetcher → `claude_grade`) before fixing.
3. Always use `--channel <id>` when running `tracker.py --live` locally — unscoped runs broadcast to production.
4. **Log queries: mind the timezone.** `journalctl --since/--until` uses the VPS **local time (America/New_York, EDT)**, but `graded_at` (DB/cache) and Telegram `ts` are **UTC**. Subtract 4h (UTC→EDT) or the query misses entries.
5. **`systemctl is-active` lies about hangs.** Verify liveness by the recency of its last log line, not `is-active` alone. But log recency is only a liveness signal for a unit that logs every cycle — `grade-daemon` prints `[cycle N]` only when `graded > 0`, so a healthy idle daemon is silent for hours and reads as wedged. For those, check `NRestarts` + `WatchdogUSec` (`systemctl show <unit>`): it feeds `WATCHDOG=1` each loop, so systemd would already have restarted it if it were hung.
6. **`vps_msg.py`/Telethon need the `-100`-prefixed channel ID.** A `t.me/c/<short>/<msg>` link gives the short ID; prepend `-100` or calls fail.
7. **"Didn't run" usually means "ran and crashed."** For a scheduled job (cron/timer) that "sometimes doesn't fire," read its output log (`/tmp/*_cron.log`, `journalctl -u <unit>`) for a traceback BEFORE suspecting the scheduler — it usually ran fine and died late in the pipeline. The fix is resilience (retry + explicit timeouts), not the schedule.
8. **"Parsed as UNKNOWN" is usually a coverage gap, not a parse failure.** When a pick parses correctly (right sport/teams/bet_type) but grades UNKNOWN, suspect the score fetcher's competition list, not the parser — UNKNOWN comes from `build_context` returning `CONTEXT_SKIP` when the fetcher finds no game, often because the league isn't in its list (e.g. `SOCCER_LEAGUES`). Verify by hitting the ESPN scoreboard for the right league code (`soccer/swe.1`, …) directly; if ESPN has the game, add the code to the fetcher's list.
9. **"Nothing happened" may just be "not processed yet."** Before diagnosing why odds/grading didn't happen for a pick, compare the message post time (Telegram `ts`, UTC) against the last `telegram-tracker` cycle (`systemctl list-timers`, EDT — subtract 4h). The tracker runs every 5 min; a pick posted after the last run simply hasn't been scanned yet, and no cache entry will exist. A missing cache entry + a message newer than the last cycle = wait for (or manually trigger) the next run, not a bug. `tracker.py --live --channel <id>` processes it immediately.
10. **A "sent twice" duplicate is often a source-side delete-and-repost, not a listener race.** The listener dedups on `(channel, dest, msg_id)`. When a capper deletes and re-posts (or double-taps send), the repost gets a **new msg_id**, so both copies pass the id guards and forward. Ground truth is the `listener_forwarded` table (`sqlite3 picks.db`): a duplicate shows as two adjacent source ids with the same content. Confirm by fetching each id directly (`get_messages(src, ids=<id>)`, NOT topic-filtered — a deleted/reposted id can be invisible to a topic-scoped fetch); the earlier usually returns `<none>` (deleted at source). Fix is content-dedup, not id-dedup.
11. **`sport=Other` + `odds_match_type=sport_unsupported(Other)` = an entirely unsupported sport, not a mis-parse.** Distinct from lesson #8 (sport supported, league/competition missing): here the sport isn't in the parse enum at all, so Claude falls back to "Other", which skips odds (`sport_unsupported`) and grading (`build_context` → `CONTEXT_SKIP` → UNKNOWN). Adding a new sport is a 3-line pattern: enum in `_PARSE_PROMPT` (`ai.py`) + `ESPN_LEAGUES` (`scores.py`) + `SPORT_KEYS` (`odds.py`); check The Odds API `/v4/sports/?all=true` and the ESPN `site.api...` scoreboard for the right keys first (e.g. PLL lacrosse = `lacrosse_pll` / `lacrosse/pll`). Add a post-parse safety net + prompt team roster like the WNBA/CFL blocks so nicknames resolve to canonical full names.
12. **A code fix to the parser does NOT retroactively re-parse already-cached picks.** The tracker reuses `cached["parsed"]` and skips `claude_parse` on subsequent runs (to avoid re-paying), so after you fix a classification/team/bet_type bug and deploy, the offending pick STILL shows the old wrong parse. You must invalidate its `parse_cache.json` entry to force a fresh parse. For a **non-forwarded-only** channel, delete the whole `<channel>:<msg>` entry (tracker re-parses from scratch on the next run). For a **forwarded-only** channel, do NOT delete it — the tracker's gate requires `"parsed" in entry` (or `_forwarded`), so a deleted entry gets skipped; instead edit the parse in place and drop `odds_by_pick` to re-fetch. Check membership with the `grade_forwarded_only` flag in `MAPPINGS_CONFIG`. Then run `tracker.py --live --channel <id>` to verify. (Restart `grade-daemon` first if the fix touched grading code — it's a persistent process and won't see the new code until restarted, and stopping it during the cache edit also avoids a re-grade race.) **Keep it stopped through the verification run too, not just the write.** The daemon polls every 10s and only calls `_insert_emojis` — never `_insert_odds`, because it assumes an earlier tracker pass already stamped the tag. So if it reaches a hand-repaired entry before your tracker pass does, it stamps the emoji onto text that never got its odds tag (`mega max.❌` instead of `mega max. [+102]❌`), and the tracker then reports a clean `edit:1` over the degraded result.
13. **A fix that changes WHERE a tag/emoji lands in a live-edited message must be idempotent.** The tracker rebuilds the edit from the *current live message text* every cycle (`_to_bot_html(text) → _insert_odds/_insert_emojis`), so placement logic that recognizes the header/target line before the tag is appended but not after (e.g. matching a `Parlay:` label by a trailing colon, which `Parlay: [+101]` no longer has) will re-fire on the next run and **double-tag**. Make the detector tolerate its own already-placed tag, and verify by applying the function **twice** (pass1 == pass2) AND by letting one real tracker cycle run over the live message — a one-shot unit check passes while production still regresses. When correcting the live message, **strip the OLD tag first**, don't just add the new position (the code won't remove a stray tag on a line it no longer selects). Update the cached `html_text` too — the grade daemon edits from that cache, not live text.
14. **A grading-RULE bug mis-grades a whole CLASS of picks — sweep for siblings, don't fix only the reported one.** Calc shows the correct numbers but the wrong verdict ⇒ the bug is the rule (`_GRADE_PROMPT` in `ai.py`), not the fetcher/context. After the rule fix, query the `grades` table for the others the gap hit (e.g. F5/1H ML `verdict='LOSS'` whose `calc` mentions a tie) and correct EACH across all 4 artifacts: the `grades` row (the angles dashboard reads its `verdict` column; PUSH=0 profit, LOSS=negative), `parse_cache.json` `leg_verdicts` (skip if pruned; set `verdict`+`broadcasted=True` so daemon/tracker leave it alone — stop the daemon during the cache write), the live pick-message emoji, and the broadcast-results message (only if the channel has a `broadcast_results_channel`). Anchor the emoji swap on the odds string (`-140❌`→`-140♻️`) so a capper's own ❌ flair isn't clobbered; EDIT the stale broadcast in place, don't re-broadcast (a new post leaves the wrong result in the feed).
15. **A green systemd status can be a lie told by a pipe.** `cmd | tee "$LOGFILE"` returns *tee's* exit code (always 0), so without `set -o pipefail` a crashed job reports `status=0/SUCCESS`, skips its retry loop, and pings healthchecks.io as a *success*. When a scheduled job quietly stopped doing its work but every status light is green, grep the runner for `pipefail` before believing the green. Related: a job that returns empty results (`0 fetched`, `no new items`) instead of raising turns a hard outage into a normal-looking quiet day — missing credentials/auth should exit non-zero and page, not return `[]`.
16. **A fresh worktree has no `.env`, `.env.local`, or `picks.db`** — they're gitignored, so a script run there dies on config load (`KeyError: 'TELEGRAM_API_ID'`) and it looks like your edit broke something. Symlink them in first: `ln -sf /home/forwarder/app/{.env,.env.local,picks.db} .` — and `rm` the links before `git add -A`.
17. **"Bad credentials" is a conclusion, not an observation — don't let a sentinel return value name a cause.** A library that signals failure with `None`/`[]` makes an internal bootstrap failure indistinguishable from an auth rejection (twscrape's `user_by_login` returned `None` because its own anti-bot token generator scraped a page the site had migrated — the cookies were fine, and my error message confidently told the user to refresh them). Before blaming a secret: (a) confirm rotating it actually changes the bytes sent — libraries cache credentials in their own store (`accounts.db`, keyrings, `~/.config/...`) and silently no-op your config write, so you may still be testing the OLD secret; (b) confirm the library's own setup step succeeded — read the WARNING lines you're tempted to skip past; (c) check the installed version is already latest before hand-patching upstream. Word the error for what you actually verified.
18. **A "still broken" test result can be your own harness silently reverting the fix — verify the fix actually runs in the failing path.** When you test a fix via an override (monkeypatch, env var, edited config) while still calling through the production wrapper, a setup/factory/idempotency-guard can re-apply the ORIGINAL, so your override never takes effect and the unchanged failure is a *false negative* — which can re-confirm the wrong root cause. (A manual `XClIdGen.create`→working-URL patch was clobbered by `build_api()`'s own `patch_xclid()` re-applying the broken URL via its `_home_patched` guard; the resulting `None` nearly re-blamed the cookies.) After editing the SOURCE, re-test through the real entry point rather than a hand-rolled override, or assert your override is the one in effect at the failure point. Code-path sibling of #17(a).
19. **A sibling artifact succeeding does not refute a race — it dates it.** When one item fans out to N destinations (see the multi-dest pattern) and only some got processed, that is NOT evidence the failing one took a different code path. One sequential pass over channels/items can straddle the triggering event, catching whatever it reaches *after* and missing whatever it already passed — so the success/failure split locates the scan window instead of disproving the race. (A pick forwarded to two channels at 19:05:59 got odds in 18s in the one scanned *after* the post and waited 4m14s in the one scanned 3s *before* it; the working copy nearly made me discard the correct root cause.) Get per-artifact processing timestamps (Telegram `edit_date`, DB `graded_at`) and order them against the event before concluding two mechanisms are in play.
20. **"Clear the cache and let it re-fetch" replays the fetch at *today's* state, not the state you're repairing.** A documented invalidate-and-refetch recipe assumes the world still looks like it did at capture time. Re-run it after the underlying event has moved on and the refetch silently binds to a *different* subject — a live line instead of the pregame one, the next game in the series instead of the one you're fixing — and the resulting wrong date/id then propagates into everything downstream that keys off it. Worse, it *looks* like it worked: fresh values, no errors. Before invalidating, ask whether the source is still serving the same snapshot; if not, write the corrected values in directly from a time-anchored source (a historical/closing endpoint pinned to the original timestamp or id). Validate by checking that a field which was *already correct* reproduces byte-for-byte — if it doesn't, your refetch is pointed somewhere else.
21. **A clean re-run proves nothing if the item was already marked done — confirm the run actually reached your change.** Re-running the pipeline over the affected item *after* the original event settled it returns `0 errors` because a terminal/dedup/"already processed" flag skips it long before your edited code. The green is vacuous. Mirror of #18: there the harness silently reverted the fix, here it never invoked it — and both read as a confident result. (A `tracker --target` pass over the two affected messages returned `edit:0 fail:0 err:0`; both were `broadcasted=True` and skipped entirely.) Verify with something only the changed code can produce: check the item appears in the run's own output, or rebuild the triggering condition on a throwaway subject (test-channel message, scratch row) and drive the **real** entry point over it. Sibling of #20 — the state you need to test with is usually the state the original event consumed.
22. **A 0-diff sweep over cached/persisted state can mean "never exercised", not "clean" — check the corpus contains the broken artifact's inputs.** Sweeping for siblings or regressions by replaying stored rows is only as good as what got stored, and the paths most likely to be buggy are often the ones that format *live or derived* data the cache never holds. (Replaying `_insert_odds` over all 187 priced `parse_cache` entries reported zero output changes — for a bug that was live in two messages, including the reported one. The `_dupe` path feeds the *duplicate's* live text through the formatter using the *primary's* parsed picks, and a dupe entry is only `{"_dupe": true, "primary_id": N}`; 0 of 4 dupes were even visible to the sweep's filter.) Before trusting a clean sweep, assert the specific failing case is IN the corpus — replay it and watch the known-bad output reproduce. If it doesn't, the sweep is measuring the wrong population: re-run it against live artifacts. Same false-confidence family as #21, one level up — there the run skipped the item, here the corpus never contained it.
23. **When sweeping for siblings, filter on a fingerprint of the *producing code*, not on the symptom.** Artifacts that merely look like the broken one flood the results: the symptom (no emoji, no grade, no cache entry) is also what a human's manual post, an already-graded forward, or a genuinely contentless item looks like. Sender/channel is often NOT a discriminator — the userbot and the operator share one Telegram account. (A first sweep flagged 7 "dropped" albums; 6 were false positives and only 1 came from the buggy path.) Pick a signature only the suspect code emits — a `source_label` suffix it appends, the reply-chain parent it sets, where the library puts an album caption — and confirm the known-bad artifact matches it before trusting the count. Complement of #22: there the corpus was too small, here it is too broad.
24. **A flat, round-the-clock rate of identical work is a retry loop, not real volume — look for a failure state nothing persists.** Cost or call-rate that jumps to a *plateau* and holds there (same per-unit cost, ~1 per cycle, unchanged overnight and on quiet days) is not driven by traffic; it is one stuck item re-attempted every cycle forever. The usual cause is an outcome the code treats as "not resolved" but never writes down, so the item never leaves the work set — and a loop that scans a whole cache with no age cutoff will keep probing it indefinitely, long after the tracker's own `--days` window would have dropped it. (One mis-parsed pick whose context resolved to the *wrong game* graded UNKNOWN every attempt; only WIN/LOSS/PUSH are persisted, so daemon + tracker re-asked Claude ~1,730x/day for 5 days — ~$9.40/day, the entire 90x spend spike, from a single pick.) Diagnose by replaying the decision path over the whole pending set and counting how many items actually reach the expensive call — if the answer is 1, one item is the whole bill. Then check that terminal states are persisted *including the failure ones* (writing a verdict the resolved-test doesn't accept changes nothing), and that any unbounded loop has an age cutoff.
25. **Stopping a loop by writing a flag proves nothing until the flag survives the next writer — time the verification to span one full cycle of every process that writes the store.** A shared store rebuilt from a template rather than mutated in place carries forward only an allowlist of keys, so a flag that isn't on the list is silently dropped by the next run that re-processes the entry: its lifetime is one write cycle, not forever. The behaviour really does stop in the meantime, so a window that fits inside that lifetime confirms the *mechanism* while the claim you actually need — "it's fixed" — is false, and the symptom count reads as a clean pass. (Marking a runaway pick `_failed` stopped it dead; 5 minutes later `_pending_entry` in `tracker_cache.py` rebuilt the entry without `_failed` and the daemon resumed 12s after that. My verification sat entirely inside the gap. Tellingly, the same file's prune logic already treated `_failed` as durable — the intent was right and only the rebuild defeated it, which is why the flag looked like a supported terminal state.) Re-read the flag *after* a writer has run, not just the symptom during; and when a store has several writers, stopping one of them is not quiescence.
26. **A trailing-window alert reports history, not now — ask "is it still happening?" before asking "what's causing it?"** Any rolling-window monitor (24h spend, 7d error rate, rolling p99) keeps firing for a full window after the cause is fixed, so an alarm can page about a solved incident. Bucket the metric by hour and find the edge *first*: a high window total with a near-zero current bucket means you are watching the window drain, and there is nothing live to chase. (A $3.85/24h spend alarm was ~10h of pre-fix tail from an already-capped pick; spend had been $0.00 for six hours when it fired.) The histogram both dates the burst and reveals its shape, so it costs nothing as a first move. If the alert body carries no current-interval figure, add one — that is the field that tells the two apart on sight.
27. **When a pick turns on an ambiguous nickname, BOTH readings can grade cleanly — disambiguate from outside the pipeline, and mine your own history before any external API.** "Snakes -1.5" reads as the Diamondbacks to anyone who knows US betting; it was the Maryland Whipsnakes. Each had a real game that day, a real closing line, and a clean verdict — *opposite* ones (ARI won 12-8 ✅ / Whipsnakes lost 13-14 ❌) — so nothing downstream would have flagged the wrong one and "it graded fine" proves nothing. A confident reading is the dangerous failure mode precisely because it verifies. Resolve it from context the pipeline cannot see: (a) the capper's own history — which sports do they ACTUALLY bet, and how do they phrase this bet type (`parse_cache.json` `html_text` is greppable, free, and instant); (b) the pregame window — which candidate game started shortly *after* the post; (c) when the message names a person ("fading/tailing @X"), that person's public feed, which is ground truth for which side a fade lands on. Do (a) first: our own cache already held the answer ("Tailing @krabs_bookit on Outlaws ML", 7 days earlier) while the rate-limited X calls were still sitting in a 15-minute queue.
28. **A cap on the expensive branch leaves the cheap branch unbounded — and a cost monitor is blind to the loop that costs nothing.** Lesson #24 frames runaway loops as a spend signal, which silently assumes every retry reaches the paid call. Put the attempt counter *at* that call and the failure that gives up earlier (no match found, unsupported input, an early `continue`) never counts an attempt, so it retries forever for free: no spend alarm, no error rate, nothing but volume in a log nobody tails. (A parlay leg naming a fighter who wasn't on any card context-skipped before `claude_grade`, so the ungradeable cap never engaged; it re-posted to the audit channel every 5 min for 534 cycles at $0.00.) Count attempts on the *outcome* ("still unresolved after this pass"), not on the branch that happens to be billable — and when hunting a loop, measure its rate in actions, not dollars.
29. **The anomaly you spot in the broken record is only a cause if healthy records don't share it — run the base-rate check before you write it down.** A failing item always has something odd about it, and the odd thing is usually innocent. Grep the corpus for other records carrying that same value and see how many are fine; if most are, you have a coincidence and the real cause is still out there. (I named `sport: null` as the reason a leg never resolved and put it in the commit message and CLAUDE.md — then found 60 picks in the cache with `sport: null` grading perfectly well, because it falls back to the top-level parse. The actual cause was a fighter name matching nothing on the scoreboard.) The check costs one grep and it belongs *before* the commit, not in a follow-up correcting the explanation.
30. **A new cleanup or terminal rule fires against the entire accumulated backlog on its first run, not just future cases — count the blast radius before deploying, not after.** Retention rules, staleness sweeps, new validations and new alerts all apply retroactively to every row already in the store, so the first cycle is the loudest one the rule will ever have. Simulate the predicate over the current store and count the hits first; then decide whether the first run should notify, log quietly, or be seeded as already-handled. (A 3-day staleness retire fired on 16 dead entries at once, each sending an audit notice — into the very channel I had just been asked to stop spamming.) A rule that is right about every one of those rows can still be wrong about announcing them all at once.

31. **Restart last. Any VCS operation after the restart silently replaces what you deployed, and every status check still reads clean.** `git pull --rebase`, `stash pop` and `checkout` all rewrite working-tree files, so a service restarted before them is running different bytes than `git log`/`git status` now describe — the commit is present, the tree is clean, and the process is stale. (I committed, restarted the listener, then rebased onto an upstream commit; the rebase rewrote `common.py` 39s *after* the process started. Benign only because it re-applied an identical diff — had upstream touched that file I'd have reported a deploy that never loaded.) Either make the restart the final step, or verify against the commit the process actually loaded: `git diff <that-commit> -- <files>`, not mtime and not `git status`.

32. **The old code is the baseline, never the database — A/B the same path on the same inputs.** Diffing a replayed fix against stored values conflates your change with every difference between the path you replayed and the path that wrote the record, and the result reads as a regression you didn't cause. (Replaying the historical odds lookup over cached picks showed 53 differences; almost all of those picks had been priced by the *current* endpoint at post time, so the diff was measuring snapshot drift. Checking the pre-fix commit out into a second worktree and running both against one DB copy gave the real answer: 16 changed, every one a wrong-game binding corrected.) Two worktrees, one input snapshot.
