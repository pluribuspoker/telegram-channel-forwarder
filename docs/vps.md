### Switching to test mode

**Locally** (no stop/start needed — uses local `.env.local` sessions):
```bash
python listener.py --test
```

**On VPS** (must stop the live service first):
```bash
stop
su - forwarder
cd ~/app
~/venv/bin/python listener.py --test
# Ctrl+C when done
exit
start
```

In both cases, `test_source_channel` → `test_dest_channel` from `MAPPINGS_CONFIG`, and all `filter_pattern` checks are bypassed.

### Ubuntu update notifications (`deploy/sbin/` → `/usr/local/sbin/`)

Ubuntu security updates land via `unattended-upgrades` (runs inside `apt-daily-upgrade.service`, typically the ~6:30 AM ET window) and come in two classes, each announced in the **watchdog bot chat** with the `pickbot:` prefix:

- **Library-class** (zlib, util-linux, coreutils, …): no reboot needed. Packages install in minimal steps and **needrestart cycles every service holding a replaced library after each batch** — the whole box bounces (forwarder, grade-daemon, ssh, the Claude session…), and a service can legitimately bounce **twice** in one window (restarted early, then a lib it maps — e.g. zlib for node — replaced by a later batch). `update-notify` (ExecStartPost drop-in `apt-daily-upgrade.service.d/update-notify.conf`) announces once per run that changed packages: count, first packages, "restarted in place; no reboot needed" (or a pending-reboot note). Silent on the no-change days. Test: `DRYRUN=1 WINDOW_MIN=600 /usr/local/sbin/update-notify`.
- **Reboot-class** (kernel, apparmor → `/var/run/reboot-required`): `auto-reboot.timer` (daily 06:00) runs `reboot-if-required` — DMs "pickbot: rebooting now to apply updates (pkgs)…" and reboots; `boot-notify.service` DMs "back online after reboot" (+ any failed units) after boot. A flag set by the ~6:30 run reboots the **next** morning at 06:00.

Diagnostics: both restart types show clean `Stopping→Started` pairs with `NRestarts=0` (explicit restarts, not crashes); the tell for the library-class window is a whole-box storm of `Consumed … CPU time` stop lines in the journal plus fresh `Start-Date` entries in `/var/log/apt/history.log`. Do **not** suppress needrestart for individual services — that leaves them running deleted, unpatched libraries. The Claude session's "▶️ Restarted" ping stays a bare resume pointer **by design** (2026-09-01: a cause note was added, then reverted in favor of this family — one consistent announcement channel for every update-driven restart). Incident that motivated all this: 2026-09-01, two unexplained 6:31/6:33 AM session restarts; the operator had only ever seen the reboot-class announcements (last: 2026-08-25, apparmor).

### Claude Code via Telegram (Channels)

Claude Code runs on VPS in a tmux session with the official Telegram channels plugin. The user DMs `@ForwarderClaudeBot` on Telegram to interact with Claude Code — full CLI features (skills, hooks, memory, dangerous mode) work.

- **tmux session:** `tmux attach -t claude` (as forwarder user)
- **Restart:** `sudo systemctl restart claude-channels` — the unit rebuilds the tmux session through `run_claude_channels.sh`, which picks up the currently selected model (see *The model is state* below). The conversation and its context are lost.
- **Logs:** `su - forwarder -c "tmux capture-pane -t claude -p -S -50"`
- **Bot token:** `~/.claude/channels/telegram/.env` (forwarder home)
- **Access config:** `~/.claude/channels/telegram/access.json`
- **Hooks/settings:** `/home/forwarder/.claude/settings.json` and `/home/forwarder/.claude/hooks/`
- **Plugin:** `telegram@claude-plugins-official` v0.0.6, requires Bun (`/usr/local/bin/bun`)
- **Context reset:** ⚠️ Sending `/clear` in Telegram does **not** reset context — the plugin only handles `start`/`help`/`status`, so `/clear` is forwarded as a plain message and does nothing. The context is one continuous session until the `claude` process is restarted. Telling the Claude bot itself "restart"/"reset" works: the session self-restarts via the detached restarter below (2026-09-10); the watchdog bot's `/restart` remains the out-of-band path for when the session is wedged or dead.

**Self-restart from the Claude chat (`deploy/restart_and_ping.sh`, 2026-09-10).** When the operator asks the Claude session for a restart/reset, the session sends a one-line reply ("restarting — back in ~1 min"), then launches the detached restarter and lets itself be killed:

```bash
sudo -n systemd-run --collect --unit="claude-restart-$(date +%s)" \
  /home/forwarder/app/deploy/restart_and_ping.sh <chat_id>
```

Why the detour: `claude-channels.service` has `KillMode=control-group`, so any restart kills the session **and every process it spawned** — an inline `sudo systemctl restart` from the session dies mid-call (PID 1 still finishes the job, but nothing survives to confirm the outcome), and the pre-service `setsid`+raw-tmux approach now races the supervisor loop. `systemd-run` places the script in its own transient scope, outside the doomed cgroup. The script settles 5s (slack for the goodbye reply to flush), restarts the service, then waits up to ~2 min for the full stack — tmux session + `claude --channels` process + `bun server.ts` poller — and pings the chat "✅ Back online" through the plugin's own bot token (`~/.claude/channels/telegram/.env`, direct `sendMessage`, no getUpdates so no 409 risk). That ping is a stronger up-signal than the SessionStart "▶️ Restarted" resume pointer, which fires before the receive loop is ready; the definitive receipt is still the 👀 on the next message, and messages sent during the restart window are still silently dropped. On timeout it pings ⚠️ pointing at the watchdog bot (`/status` `/logs` `/restart`). Unique `--unit` names plus `--collect` keep a failed transient unit from blocking the next attempt; `<chat_id>` defaults to `WATCHDOG_USER_ID` from `~/app/.env` when omitted. Dry-run: `sudo /home/forwarder/app/deploy/restart_and_ping.sh --check` (validates chat id, bot token via `getMe`, stack liveness; no restart, no message).

**/restart is in the Claude bot's command menu** (operator chat, 2026-09-10). The plugin forwards any slash command it doesn't handle as a plain message, so a menu tap arrives as literal `/restart` text and triggers the self-restart flow — it needs a live session to act, so recovery from a wedged/dead session stays with the watchdog bot. Registration is **chat-scoped**, which is load-bearing: the plugin's poller rewrites the `all_private_chats` scope with only start/help/status on **every** boot (`onStart` → `setMyCommands` in `server.ts`), but for a private chat the `chat` scope outranks `all_private_chats` and the plugin never touches it, so the custom menu survives restarts. A chat-scoped list fully replaces the visible menu, so it re-lists the stock three alongside `restart`. Re-register (after a bot-token change, or to edit entries):

```bash
TOK="$(sudo grep '^TELEGRAM_BOT_TOKEN=' /home/forwarder/.claude/channels/telegram/.env | cut -d= -f2- | tr -d '\r\"')"
curl -s "https://api.telegram.org/bot${TOK}/setMyCommands" -H 'Content-Type: application/json' \
  -d '{"scope":{"type":"chat","chat_id":5911202683},"commands":[
    {"command":"restart","description":"Restart Claude — fresh context (~1 min)"},
    {"command":"status","description":"Check your pairing status"},
    {"command":"help","description":"What this bot can do"},
    {"command":"start","description":"Welcome and setup guide"}]}'
```

**The model is state, not a constant: `/model` in the watchdog bot.** `run_claude_channels.sh` reads `CLAUDE_CHANNELS_MODEL` and `CLAUDE_CHANNELS_EFFORT` out of `/home/forwarder/.claude-channels.env` at every start, falling back to `claude-opus-5` / `max`. `bash deploy/run_claude_channels.sh --print-model` prints what a restart would use and is the *only* place that resolution happens, so the bot's answer can't drift from the launcher's behaviour. The file lives **outside the repo** deliberately — a `git pull` or a `syncenv` must never move the session back onto a model the account can't bill.

Switching from a phone is `/model opus|fable|sonnet|haiku` (or a full id) in the watchdog bot. It types `/model <id>` into the live tmux pane rather than restarting, because a restart throws away the conversation — on 2026-09-11 that was 160k tokens of in-flight work. **A switch counts as confirmed only when the pane echoes the command one time MORE than it did before we typed it, with the reply under that newest echo.** "Is `Set model to…` on screen" is not an answer — the previous switch's reply is still there, and re-issuing the same command matches it in the second before the new one renders (caught doing exactly that while building this). Pane history only grows, so the echo count is the discriminator; a command Claude has merely *queued* mid-turn is echoed with nothing under it and correctly reads as unconfirmed. The one thing that overrides a timeout is `~/.claude/settings.json` *changing* to the target — the CLI writes it only for a model it accepted, so that's proof the queued command ran late. Only a confirmed switch is persisted. `/model <id> restart` skips the live step for a wedged pane — writes the file, restarts the service, context lost. `/effort low|medium|high|xhigh|max` works the same way with one difference: the CLI marks effort "this session only", so the state file is the only thing carrying it across a restart, and because the five levels are a closed set it is persisted whether or not the pane confirms.

Model names are allowlisted, not trusted, in **both** halves (`^[A-Za-z0-9][A-Za-z0-9._-]*(\[1m\])?$` — admits the `claude-fable-5[1m]` long-context ids, rejects anything starting with `-`, since the value lands on a shell command line where a leading dash reads as a claude CLI flag). The launcher fails **open**: a junk or half-written state file falls back to the default rather than refusing to start, because being on the wrong model beats a restart loop. Pinned by `scripts/test_claude_model_switch.py` (Windows-safe; the bash half skips without bash).

Run /usage-credits to continue or switch models with /model" — including the messages asking Claude to fix it, because the CLI answers that before the model ever sees the prompt. The banner reads "Claude API" rather than "Claude Max" under an env token, but usage is still on the subscription — the API returns `anthropic-ratelimit-unified-5h/7d` quota headers with `overage-status: rejected` (`org_level_disabled`), i.e. refused at the limit, not billed.

**Re-auth from a phone: `/reauth` in the watchdog bot**, which DMs a login URL; open it, then send back `/authcode <code>`. It verifies the new token against the API *before* installing it, then restarts `claude-channels`. This lives in the watchdog bot for the obvious reason — it's needed exactly when Claude itself can't answer — and works because that bot is a **separate service with its own token**, so it survives both the dead credential and the restart that fixing one requires. `claude setup-token` is interactive (prints a URL, then blocks on stdin), so it runs in a detached tmux session whose two properties are load-bearing, both learned by breaking them:
- **A dedicated socket (`tmux -L authtok`).** On the default socket the tmux server is a child of `claude-channels.service`, so `KillMode=control-group` destroys it on any restart — including the restart re-auth performs at the end. A `setup-token` session started on the default socket was killed mid-flow this way, taking its one-time code with it.
- **A wide pane (`-x 400`).** The CLI hard-wraps output to the pane width, so at 80 cols a 108-char token is captured as 79 chars. That truncated token *looks* like a token and installs cleanly; it only fails later, at the next restart. `finish_reauth` refuses anything under 100 chars and probes the token before writing it.

**Triggering the investigate skill (shorthands for `/investigate`):** A message that starts with `inv ` OR that reports a pick/grading problem or asks why something did/didn't happen (especially with a `t.me/...` link) is an investigation request — invoke the **investigate skill** (a real Skill tool call, so the once-per-investigation lessons hook counts it). Don't answer these ad-hoc.

**When running on VPS via channels**, this Claude instance can run commands directly (no SSH needed). Check `uname -s` or hostname to detect environment (VPS hostname is `pickbot`). As the `forwarder` user, `systemctl` needs `sudo -n` (passwordless sudo works, e.g. `sudo -n systemctl restart grade-daemon.service`) — the bare `stop`/`start`/`restart` aliases are interactive-SSH-only. `git` commit/push work directly from `~/app`.

**Delivery receipts (👀) are automatic via a hook.** A `UserPromptSubmit` hook (`telegram_seen_react.py`) reacts 👀 to every inbound Telegram message the instant the harness receives it — a hard delivery receipt at the harness level (not a model tool call, so it can't be forgotten or lost to a mid-turn crash). **Reaction present = the session received the message; reaction absent after a few seconds = it was dropped, resend it.** Drops happen because the Bot API has **no history/backfill**, so a message sent during a restart window (before the new process's poll loop is connected) is silently lost — and no hook fires for a message the process never received, which is exactly why the *absence* of the 👀 is the tell. Note the resume-notify hook's "▶️ Restarted… copy this back to resume" message is posted by the SessionStart hook and does **not** prove the receive loop is ready; wait for the 👀 on a fresh message before firing the real task.

The tracker and grade daemon share `parse_cache.json` (atomic writes via `os.replace`). The daemon grades picks fast; the tracker handles Telegram reads, parsing, and odds. When the daemon grades a pick, it sets `broadcasted=True` in the cache so the tracker skips it.

**Broadcasting is daemon-only.** The grade daemon is the sole broadcaster (calls `audit.broadcast_results`). The tracker no longer broadcasts — it grades and edits emojis, but the daemon handles result broadcasting and Google Sheets logging. The listener's `_trigger_tracker_soon()` is debounced (one concurrent run max) to avoid race conditions with the daemon.

### Environment files

Environment split to protect server-only secrets from `syncenv` and keep the
NFL Guesser's Odds API quota isolated:

| File | Where | Synced | Contains |
|---|---|---|---|
| `.env` | local + server | ✅ `syncenv` copies this | config that exists on **both** machines |
| `.env.local` | local + server (separately) | ❌ never touched | `TELEGRAM_SESSION`, `BOT_SESSION`, `X_AUTH_TOKEN`, `X_CT0`, `PIKKIT_TOKEN` |
| `.env.guesser` | server only | ❌ never touched | `ODDS_API_KEY` override loaded only by `nfl-lines-fetcher.service` |
| `~/.claude/auth.env` | server only | ❌ never touched | `CLAUDE_CODE_OAUTH_TOKEN` for the channels session **and** `god-judge.service` (both units load it) |

`GOD_JUDGE_*` overrides (`GOD_JUDGE_HEALTHCHECK_URL`, `GOD_JUDGE_CLAUDE_ISOLATION`, `GOD_JUDGE_MAX_GAMES`, …) are synced config and belong in `.env`.

> **Rule: any value that exists only on the server belongs in `.env.local`.**
> `syncenv` *overwrites* the server's `.env` with the local copy, so a key present in the server's `.env` but absent from the local one is **silently deleted** on the next sync. This is not hypothetical: it wiped `X_AUTH_TOKEN`/`X_CT0` on 2026-07-19 and took the Trent watcher down for 2 days without a single alert. `syncenv` is safe to run freely *only as long as this rule holds*.

`.env.local` is loaded after `.env` in both Python code and systemd, so it always wins.
For the NFL Guesser only, systemd then loads `.env.guesser` last. Keep the
paid/guesser key there so graders and the quota watchdog continue using the
shared key from `.env`.

**Regex escaping in `MAPPINGS_CONFIG`:** The JSON value is inside single quotes in the `.env` file, so regex backslashes need **four** backslashes (`\\\\`) to survive: shell quotes → JSON string → regex. For example, `\d+` becomes `\\\\d+` in `.env`.

```bash
python scripts/get_bot_session.py  # generates BOT_SESSION
```
